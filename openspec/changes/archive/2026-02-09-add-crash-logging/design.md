## Context

应用 (sidekick) 是一个使用 Wails 框架构建的桌面应用，支持 Windows、Linux 和 macOS。目前的日志机制依赖 Wails 的 `runtime.LogErrorf`，仅在开发工具中可见，应用崩溃后日志随之丢失。

Windows 平台上大量使用 Win32 API（`user32.dll`, `dwmapi.dll`）进行窗口操作，这些 syscall 调用是潜在的 panic 源。`checkTarget()` 函数运行在独立的 goroutine 中，以 50ms 间隔轮询，其中的 panic 会直接导致进程退出。

当前没有任何错误持久化机制，用户报告的"自行关闭"问题无法追溯。

## Goals / Non-Goals

**Goals:**
- 在应用运行目录下建立 `logs/` 日志目录，持久化存储运行时错误信息
- 每个错误事件生成独立的日志文件，包含完整的堆栈跟踪和上下文
- 在关键代码路径（`main()`, `checkTarget()` goroutine）安装 panic 恢复器
- 日志模块全平台通用，使用 Go 标准库实现

**Non-Goals:**
- 不构建完整的日志框架（如日志级别、日志轮转等）
- 不替换现有的 `runtime.LogErrorf` 调用，仅在关键崩溃点补充文件日志
- 不实现远程日志上传
- 不实现日志文件的自动清理/轮转策略（后续需要时再添加）

## Decisions

### Decision 1: 日志存放位置 — 应用运行目录 `./logs/`

**选择**: 在 `os.Getwd()` 返回的目录下创建 `logs/` 子目录。

**理由**: 应用是"便携式"设计，所有数据（`config.json`, 数据库, `images/`）都存放在运行目录下。日志放在同一位置符合现有的文件组织模式，且用户可以方便地找到和发送日志文件。

**替代方案**: 使用 `%APPDATA%` 或 `os.UserConfigDir()`。不采用是因为会打破便携式设计的一致性。

### Decision 2: 每个错误事件一个独立日志文件

**选择**: 每次错误生成格式为 `{时间戳}_{错误类型}.log` 的独立文件。

**理由**: 
- 便于识别和分享特定的错误报告
- 避免单个日志文件持续增长
- 用户可以简单地将最近的 `.log` 文件发送给开发者

**替代方案**: 单一日志文件（`app.log`）追加写入。不采用是因为不便于关联特定的错误事件。

### Decision 3: 使用 Go 标准库 `runtime/debug.Stack()` 获取堆栈信息

**选择**: 使用标准库获取堆栈跟踪，不引入第三方日志库。

**理由**: 项目目前无日志依赖，标准库的 `runtime/debug.Stack()` 足以提供完整的 goroutine 堆栈信息，满足排查需求。

### Decision 4: panic 恢复策略 — `main()` 写入日志后退出，`checkTarget()` 写入日志后继续运行

**选择**:
- `main()` 中的 panic：写入日志后让应用退出（无法恢复的错误）
- `checkTarget()` goroutine 中的 panic：写入日志后恢复，让轮询继续运行

**理由**: `checkTarget()` 是窗口跟随的辅助功能，即使发生 panic 也不应导致整个应用崩溃。而 `main()` 中的 panic 通常意味着不可恢复的错误。

### Decision 5: 日志初始化时机 — 应用启动时立即初始化

**选择**: 在 `main()` 函数最开头初始化日志目录，早于所有其他组件。

**理由**: 确保即使在启动阶段发生的错误也能被捕获和记录。

## Risks / Trade-offs

- **[磁盘空间]** → 没有日志清理策略，长期运行可能积累大量日志文件。缓解措施：每个日志文件体积很小（几 KB），短期内不会成为问题；后续版本可增加清理策略。
- **[性能影响]** → 日志写入是同步 I/O 操作。缓解措施：仅在错误发生时写入，不影响正常运行路径。
- **[权限问题]** → 运行目录可能没有写入权限。缓解措施：日志初始化失败时静默降级，使用 `stderr` 输出错误信息，不阻止应用启动。
- **[并发安全]** → `checkTarget()` 在独立 goroutine 中运行，日志写入需要线程安全。缓解措施：每次写入创建独立文件，使用时间戳保证文件名唯一性，不需要加锁。
